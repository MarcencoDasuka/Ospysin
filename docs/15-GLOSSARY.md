# 15. Glossary of Terms

## Overview
This document establishes the authoritative domain vocabulary for Ospysin. Consistent terminology is essential to prevent ambiguity between human operators, system modules, and AI advisory components.

---

## Core Domain Terms

### 1. Raw Output (`raw_output`)
- **Definition**: The unprocessed, verbatim string or byte stream returned by a target host during a tool run (e.g., raw HTTP response wire bytes, unparsed WHOIS text).
- **Properties**: Strictly immutable, cryptographic hash computed upon persistence.

### 2. Parsed Data (`parsed_data`)
- **Definition**: The structured JSON representation generated by a tool's internal parser from the raw output (e.g., key-value map of response headers, list of DNS resource records).
- **Properties**: Standardized schema, indexed via JSONB.

### 3. Observation (`Observation`)
- **Definition**: An automated, factual data point or heuristic anomaly identified by code directly from `parsed_data`.
- **Nature**: Machine-generated, non-evaluative, objective.
- **Example**: *"Target response omits the Strict-Transport-Security header"* or *"robots.txt disallows /admin/backup/"*.
- **Distinction**: An Observation is **not** yet a confirmed vulnerability. It is raw technical telemetry.

### 4. Finding (`Finding`)
- **Definition**: A human-validated, contextualized security risk, vulnerability, or architectural defect.
- **Nature**: Operator-curated, qualitative, evaluative.
- **Example**: *"Exposed Administrative Backup Directory Accessible Without Authentication"*.
- **Properties**: Has an explicit status (`OPEN`, `CONFIRMED`, `FALSE_POSITIVE`, `REJECTED`), severity (`INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`), confidence level (`TENTATIVE`, `FIRM`, `CERTAIN`), remediation guidance, and supporting `Evidence`. If marked `REJECTED`, an operator justification reason (`rejectionReason`) is mandatory, and the item is excluded from active vulnerability counts while preserved in the report appendix.
- **Distinction**: An Observation becomes a Finding only when the operator reviews, verifies, and formally accepts it into the audit record.

### 5. Evidence (`Evidence`)
- **Definition**: A precise, immutable snippet, header line, or payload excerpt extracted from a `ToolResult` that substantiates a `Finding`.
- **Nature**: Verifiable proof connecting a human finding to a physical network packet.
- **Example**: Line 14 of `raw_output`: `Disallow: /admin/backup/`.

### 6. Scope Asset (`ScopeAsset`)
- **Definition**: An explicit domain, URL, IP address, or CIDR range formally approved for testing within an Engagement.
- **Constraint**: Any tool execution directed at a target outside defined Scope Assets is rejected by the Policy Engine.

### 7. Scope Acknowledgment (`ScopeAcknowledgment`)
- **Definition**: A server-side timestamped record capturing the operator's attestation of authorization prior to initiating an audit session.
- **Epistemic Boundary**: Demonstrates what text and hash the server recorded at the given timestamp; does not constitute external legal proof of ownership, third-party consent, or statutory immunity.
- **Components**:
  - `statement_version`: Semantic version of the legal terms shown.
  - `statement_text`: Exact verbatim text displayed in the UI.
  - `statement_hash`: SHA-256 digest of `statement_text`.
  - `acknowledged_at`: ISO 8601 UTC timestamp of operator confirmation.

### 8. Audit Session (`AuditSession`)
- **Definition**: An active or completed state machine tracking the sequential execution of tools against a designated target asset.
- **States**: `ACTIVE`, `COMPLETED`, `ABORTED`.

### 9. Tool Execution (`ToolExecution`)
- **Definition**: A single, timestamped execution event of a registered tool from the Tool Catalog within a session.
- **States**: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `CANCELLED`.

### 10. Audit Event (`AuditEvent`)
- **Definition**: An immutable ledger entry recording a system action, user choice, policy check, or tool transition for forensic compliance.

### 11. Policy Decision (`PolicyDecision`)
- **Definition**: The boolean gate result (`ALLOW` or `DENY`) generated by the Policy Engine before any socket is opened.

### 12. Vulnerability (`Vulnerability`)
- **Definition**: A security flaw, architectural weakness, or software misconfiguration that can be exploited by an unauthorized entity to breach confidentiality, integrity, or availability.

### 13. Exploit Surface (`ExploitSurface`)
- **Definition**: The total perimeter of discoverable endpoints, network services, open ports, JavaScript assets, and HTTP headers exposed to untrusted clients that could serve as entry points for an attack.

### 14. Attack Vector (`AttackVector`)
- **Definition**: The specific pathway or operational technique (e.g., Cross-Site Scripting via missing CSP, session hijacking via missing Cookie security flags) that could be used to exploit a discovered vulnerability.

## Comparison Matrix: Telemetry vs Risk

| Attribute | `Observation` (Automated Telemetry) | `Finding` (Vulnerability / Risk Assessment) | `Evidence` (Forensic Proof) |
| :--- | :--- | :--- | :--- |
| **Origin** | Automated tool parser | Human Auditor / Operator | Slice of `ToolResult` |
| **Mutability** | Generated on-the-fly / Immutable once stored | Edited / curated by operator | Immutable WORM record |
| **Nature** | Raw factual observation from response | Evaluated risk, severity, and impact | Concrete excerpt / byte sequence |
| **Example** | Missing `X-Frame-Options` header | Clickjacking risk on account dashboard | `HTTP/1.1 200 OK ... (header omitted)` |
